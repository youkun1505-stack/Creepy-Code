# コーディング規約・命名規則

対象：AIブライダルプランニング支援システム（Creepy Code）
対象範囲：バックエンド（Java / Spring Boot）・フロントエンド（Thymeleaf / HTML / CSS）の両方

---

## 1. 命名規則

### バックエンド（Java）

| 対象 | ルール | 例 |
|------|--------|-----|
| クラス名 | パスカルケース | `CustomerService`、`PlanController` |
| メソッド名 | キャメルケース、動詞始まり | `getCustomerById`、`calculatePrice` |
| 変数名 | キャメルケース | `customerName`、`totalPrice` |
| 定数 | 全て大文字＋アンダースコア | `MAX_PLAN_COUNT` |
| パッケージ名 | 全て小文字 | `com.creepycode.plan.service` |
| Entityクラス | テーブル名を単数形パスカルケース | `Customer`（テーブル`customers`に対応） |
| Repositoryインターフェース | `〇〇Repository` | `CustomerRepository` |
| Serviceクラス | `〇〇Service` | `CustomerService` |
| Controllerクラス | `〇〇Controller` | `CustomerController` |

### フロントエンド（Thymeleaf / HTML / CSS）

| 対象 | ルール | 例 |
|------|--------|-----|
| HTMLファイル名 | ハイフン区切り小文字 | `plan-simulation.html` |
| idの命名 | キャメルケース | `id="totalPrice"` |
| classの命名 | ハイフン区切り小文字（ブロック単位） | `class="plan-card__title"` |
| Thymeleafの変数名 | キャメルケース | `th:text="${customerName}"` |

## 2. パッケージ・ディレクトリ構成

パッケージは「機能ごと」に分ける（2026-10-07 改訂）。2人で機能を分担したときに、同じフォルダを触ってファイルがぶつかるのを減らすため。

### バックエンド

```
com.creepycode
 ├─ BridalApplication.java   … 起動クラス
 ├─ common       … 共通部品・トップページ
 │   ├─ controller   … トップページ（P-01）など共通の画面
 │   ├─ config       … 設定関連（Spring Security など）
 │   ├─ exception    … 独自例外クラス
 │   ├─ ai           … AI（Gemini API）の呼び出し・ダミーモード
 │   └─ storage      … ファイル保存（保存先フォルダ uploads）
 ├─ auth         … 会員登録・ログイン・パスワードリセット
 ├─ hearing      … 事前ヒアリング・AI深掘り質問・生成中
 ├─ plan         … マイプラン・料金シミュレーション・プランナーダッシュボード・プラン編集
 ├─ chat         … チャット（顧客・プランナー）
 ├─ evaluation   … 満足度評価（プランナー・アプリ）
 └─ admin        … 管理者画面・料金マスタ管理
```

common 以外の各機能の中は、次の5つに分ける。

```
（機能名）
 ├─ controller   … 画面・APIの入り口
 ├─ service      … 業務ロジック
 ├─ repository   … DBアクセス
 ├─ entity       … テーブルに対応するクラス
 └─ dto          … 画面⇄サーバー間のデータの入れ物
```

実装する順番は、これまでのチーム開発ルールと同じく
`テーブル確認 → Entity → Repository → Service → Controller → 画面 → 動作確認` とする。

### 画面・テーブルと機能の対応表

画面No.・テーブルNo.は基本設計書（v1.6）の番号。Entity は、そのテーブルを主に扱う機能のフォルダに置く。他の機能から使うときは、その機能の Repository・Service を呼び出してよい。

| 機能 | 画面 | テーブル（Entity の置き場所） |
|------|------|------|
| common | P-01 トップページ | ─ |
| auth | P-02 会員登録／P-03 ログイン／P-04 パスワードリセット申請／P-05 パスワード再設定 | T-01 USERS／T-02 RESET_TOKENS |
| hearing | P-06〜P-09 事前ヒアリング Step1〜4／P-10 AI深掘り質問／P-11 AIプラン生成中 | T-03 ONBOARDING_ANSWERS／T-09 ARCHETYPE_MASTER／T-10 VISUAL_IMAGES |
| plan | P-12 マイプラン／P-13 料金シミュレーション／P-15 プランナーダッシュボード／P-16 プラン編集 | T-04 PLANS／T-05 PLAN_OPTIONS／T-12 PLAN_REVISIONS／T-15 CONVERSATION_LOGS |
| chat | P-14 チャット（顧客）／P-17 チャット（プランナー） | T-07 MESSAGES／T-08 FILES |
| evaluation | P-21 満足度評価（プランナー）／P-22 満足度評価（アプリ） | T-11 PLANNER_EVALUATIONS／T-13 APP_EVALUATIONS／T-14 EVAL_COMMENTS |
| admin | P-18 管理者ダッシュボード／P-19 会員情報管理／P-20 プランナー品質ダッシュボード／P-23 プランナー管理／P-24 料金ダッシュボード | T-06 PRICE_MASTER |

### フロントエンド（テンプレート）

テンプレートもバックエンドと同じ機能名で分ける。

```
src/main/resources/templates
 ├─ common      … 共通レイアウト（ヘッダー・フッター）・使い回すパーツ・トップページ
 ├─ auth
 ├─ hearing
 ├─ plan
 ├─ chat
 ├─ evaluation
 └─ admin
```

## 3. フォーマット

- インデントは半角スペース4つ（バックエンド・フロントエンド共通）
- 1行は120文字を目安に収める
- 中括弧`{`は行の末尾に置く（改行しない）
- CSSは1セレクタにつき1プロパティ1行

---

## 4. コメントの書き方

- publicメソッドには「何をするメソッドか」を1行で書く
- 複雑な処理には理由（なぜその実装にしたか）をコメントする
- TODOコメントは `// TODO: 内容（担当者名）` の形式で残す

---

## 5. Thymeleaf特有のルール

- 共通レイアウトは `layout:decorate` で必ず継承する（同じヘッダー・フッターを毎回書かない）
- 繰り返し使うパーツ（料金カードなど）は `templates/common` に切り出す
- 画面側に複雑な判定ロジックを書かない（複雑な処理はController・Serviceで済ませ、HTML側は`th:if`程度に留める）

---

## 6. 例外処理・ログ

- 想定される異常系は独自の例外クラスを作る（例：`CustomerNotFoundException`）
- ログは `System.out.println` を使わず、SLF4Jのロガーを使う

---

## 7. その他

- 色・フォントサイズなどはCSS変数にまとめ、あちこちに散らばらせない
- id指定でのスタイル付けは避け、class指定を基本にする

---

## 既存ルールとの整合性について

この規約は、以下の既存ルールと矛盾しないことを確認済みです。

- ブランチ命名（`feature/〇〇`・`fix/〇〇`・`docs/〇〇`）
- コミットメッセージ形式（`feat:`・`fix:`・`docs:`など）
- Springの実装順序（テーブル確認 → Entity → Repository → Service → Controller → 画面 → 動作確認）
