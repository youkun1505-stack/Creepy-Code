# 1. はじめに

## 1-1. このドキュメントについて

このドキュメントは、「AIブライダルプランニング支援システム」の基本設計書です。

要件定義書（ver
2.0）では「このシステムで何をするか（機能・目的）」を決めました。この基本設計書では「その機能をどのような仕組みで実現するか（画面・データ・処理の設計）」を示します。

## 1-2. 前提条件

・要件定義書 ver 2.0（2026/06/15 P2C：Creepy Code 作成）の内容に基づく

・AIサービスとして Gemini API（Google社）を使用する（無料枠を利用する）

・開発・発表は各メンバーのPC（ローカル環境）で行い、クラウド（AWS等）には配置しない

・チャット機能はリアルタイム形式で実装する。チャットは担当プランナーの割り当て後、プランナーとの詳細調整に使用する

・プランのステータスは6段階で管理する

・パスワードリセット機能を含める（メールでリセットURLを送信する。ローカル環境ではメールを送らず、リセットURLをログに出力して代替する）

・チャット内ファイル添付機能（画像・PDF）を含める

・24時間対応はAIによる事前ヒアリング〜プラン雛形生成が担う。プランナーとのチャットは人が応対するため、即時応答は保証しない

・パスワードは8文字以上、半角英数字の両方を含むものとする

・本システムで扱う金額は概算（予定金額）であり、契約金額の確定・決済処理は対象範囲外とする

## 3-3. Gemini APIとの連携

Gemini APIは、以下の3つのタイミングで呼び出します。

・連携方法：SpringバックエンドからHTTPリクエストでGemini APIを呼び出す

・① 深掘り質問の生成時 — 入力：事前ヒアリングStep1〜4の回答（アーキタイプ・スタイル・日程・予算・タグ選択結果） ／
出力：顧客の価値観・優先順位を深掘りするための追加質問（3〜5問程度）

・② プラン雛形の生成時 — 入力：事前ヒアリングの回答＋深掘り質問への回答＋該当プランの会話履歴md ／
出力：プランの雛形テキスト／顧客が大事にしていることや削ってもよい部分などの価値観の要点（優先順位を含む）／チェックリスト

・③ 類似事例の要約時 — 入力：Oracleから抽出した過去プランとその会話履歴md ／
出力：プランナーに提示する類似事例の要約（6-6節参照）

・AI生成のプランはあくまで「叩き台」であり、最終的な提案はプランナーが責任を持って行う

・Gemini APIは過去の会話を記憶しないため、必要な文脈は毎回システム側から会話履歴md（6-6参照）として渡す

・Gemini
APIは無料枠を利用する。無料枠では送信した内容がGoogleのサービス改善に使われるため、開発・発表では架空のテストデータのみを使い、実在の個人情報は送信しない

・開発中はAPIを呼ばずに固定の文章を返す「ダミーモード」で動作できるようにし、AIの動作確認と発表時のみAPIを呼ぶ（設定で切り替える）

・類似事例はAIの記憶に頼らず、Oracle上の過去プランデータから検索・抽出し、その内容をAIに渡して要約させる（6-6参照）

・APIへ渡す会話履歴は、対象プラン1件＋類似事例最大5件までとする（1プランあたり約1万2千トークンで見積もり、最大で約7万2千トークン。Gemini
APIの入力上限内に収まる）

・AIの出力が上限に達して途中で切れた場合（出力トークン上限到達）は、生成された範囲までを保存したうえで、再生成を促すメッセージを表示する

## 7-3. テーブルの関係（ER図の補足説明）

・1人の顧客（USERS）は複数のプラン（PLANS）を持てる

・1つのプランには、割り当て後に1人の担当プランナー（USERS）が対応する（割り当て前はNULL）

・1つのプランには複数のオプション（PLAN\_OPTIONS）が含まれる

・各オプションは料金マスタ（PRICE\_MASTER）のアイテムを参照する

・1つのプランに対してチャットメッセージ（MESSAGES）が複数紐づく

・各メッセージには添付ファイル（FILES）が複数添付できる

・事前ヒアリング回答（ONBOARDING\_ANSWERS、深掘り質問への回答を含む）とプラン（PLANS）は1対1で対応する

・1つのプラン（PLANS）には複数の修正履歴（PLAN\_REVISIONS）が記録される

・1人の利用者（USERS）は複数の修正履歴（PLAN\_REVISIONS）の編集者になり得る

・合意済みになったプラン（PLANS）に対して、プランナー評価（PLANNER\_EVALUATIONS）とアプリ評価（APP\_EVALUATIONS）がそれぞれ1件以上記録される（再評価した場合は枝番
EVAL\_SEQ で複数レコードになる）

・1件のプランナー評価（PLANNER\_EVALUATIONS）には、コメント（EVAL\_COMMENTS）が0件または1件紐づく

・1つのプラン（PLANS）に対して、会話履歴（CONVERSATION\_LOGS）が1件対応する。会話履歴は利用者（USERS）にも紐づく

・1人の利用者（USERS）は複数のリセットトークン（RESET\_TOKENS）を持つ

・1人の顧客（USERS）は複数の事前ヒアリング回答（ONBOARDING\_ANSWERS）を持つ

・事前ヒアリング回答（ONBOARDING\_ANSWERS）はアーキタイプマスタ（ARCHETYPE\_MASTER）のアイテムを参照する。ビジュアル選択（VISUAL\_IMAGES）はJSON形式で画像IDを保持する形とし、外部キーは設定しない

・各メッセージ（MESSAGES）には1人の送信者（USERS）が対応する

・プランナー評価（PLANNER\_EVALUATIONS）は、評価対象のプランナー（USERS）と評価した顧客（USERS）に紐づく。アプリ評価（APP\_EVALUATIONS）は評価した顧客（USERS）に紐づく

・下の図は主要な関係のみを示す簡易図のため、送信者・評価者など利用者（USERS）を参照する一部の外部キーは省略している

## 8-2. 認証方式

・ログイン方式：メールアドレス + パスワードによるフォーム認証（Spring Security を使用）

・パスワード保存：BCrypt ハッシュ化（元の文字列に戻せない形式で保存）

・セッション管理：ログイン成功後にセッションIDを発行し、30分間操作がない場合は自動ログアウト

・ロール判定：ログイン成功時に、利用者ID（USER\_ID）に紐づく USERS.ROLE の値（CUSTOMER / PLANNER /
ADMIN）をシステムが自動で判別し、対応する画面へ遷移する

## 8-3. データ保護

・通信の暗号化：外部API（Gemini
API）との通信はHTTPS（SSL/TLS）で暗号化する。アプリ本体はローカル環境（localhost）で動かすため、ブラウザとアプリの間の通信はHTTPとする

・個人情報の保護：認証済みユーザーのみが自分に関係するデータを参照できるようにアクセス制御を行う

・SQLインジェクション対策：Spring Data JPA
を使用し、直接SQLに文字列を連結しない（JPAが内部でプリペアドステートメントを使う。SQLを直接書く場合もパラメータで値を渡す）

・XSS対策：Thymeleafテンプレートエンジンの自動エスケープ処理を使用する

・ファイルアップロード制限：添付ファイルはjpeg・png・pdfのみ許可し、1件あたり10MBを上限とする

・アップロードサイズ設定：上限10MBを有効にするため、アプリケーション設定で multipart
のファイルサイズ上限を10MBに変更する（既定値は1MB）

・会話履歴の保護：保存先フォルダに保存する会話履歴mdは個人情報を含むため、その顧客の担当プランナーのみが参照できるようアクセス制御を行う（顧客向けの閲覧画面は設けない）

## 8-4. 非機能要件

性能・可用性・運用まわりの非機能要件です。詳細設計を始める前の目安として、以下の内容で確定します。

・想定同時接続数：学内での発表を想定した規模のため、上限値は特に定めない

・稼働率の目安：ローカル環境で動かすため、稼働率の目標は設けない（PCやDockerが停止した場合は再起動して復旧する）

・バックアップ：テーブル定義と初期データはSQLファイル（リポジトリの db/ フォルダ）で管理し、いつでも作り直せるようにする

・ログ：エラーログ・アクセスログは Spring Boot の標準ログ（コンソール）に出力する
