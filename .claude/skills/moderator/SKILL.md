# 司会役の手順

### 役を呼ぶときの決まり

- 役を呼ぶときは、AGENTS.md の「受け渡しメモ」の項目のうち、その役に必要なものを書いて渡す。
  関係するファイルやチケットはパスで示し、中身を貼り付けすぎない。会話の写しや秘密情報は入れない。
- レビュー役・テスト役には、実装役の報告文を渡さない（うのみにさせないため）。
- 互いに関係しない役は並行して呼んでよい（例：調査役を複数、テスト役とレビュー役）。同じファイルを書く役は、いつも1つだけにする。
- 役の報告は、「状態」・根拠・変更したファイル・確かめていないことを見てから使う。報告どうしが食い違うとき、根拠が足りないときは、完了として扱わない。
- 役が起動できない、または必要な結果が返らないときは、司会役が黙って代わりに作業しない。止まってメンバーに理由を伝える。
  ただし、同時に動く数の上限で呼べなかっただけのときは、止まらずに1つずつ呼び直す。下の「格上げ」に当たるときは、その手順に従う。

### 格上げ（難しい作業を Sonnet 5.5 でやり直す）

Haiku 5.5 の役（調査役・実装役・テスト役・GitHub 係・記録係・文脈係・ハーネス点検）が終えられなかったときは、司会役が次の順で上げる。

1. **格上げする場面**：次のどれかに当たったとき。
   - 役が `止まった` か `失敗` と報告し、理由が「難しかった点」（情報や権限が足りないのではない）
   - 実装役の同じチケットが1回 `再発` した
   - 報告の根拠が足りない、または受け渡しメモの返し方を守れていない
2. **Sonnet 5.5 で呼び直す**：同じ役を、Agent ツールの `model` に `sonnet` を指定して呼び直す（`env` の固定で Sonnet 5.5 になるはず。実際の動作は未確認）。受け渡しメモには、前の報告の「難しかった点」と、
   すでに分かったこと（確かめた事実だけ）を足す。レビュー役・テスト役へは、今までどおり実装役の報告文を渡さない。
3. **司会役へのエスカレーション**：Sonnet 5.5 でも終えられなければ、それ以上は上げない。司会役が自分で状況を確かめ、
   進め方を変える案（機能の分け方・受け入れ条件・範囲など）を作ってメンバーに理由と一緒に見せ、「はい」をもらってから進める。
   案が作れなければ、止まってメンバーに相談する。司会役が黙って役の代わりに実装やレビューをすることはしない（AGENTS.md の「3. 役割」）。

- 格上げのとき、推論の強さは定義ファイルの `effort` のまま変えない（`model` だけを指定する）。
  格上げした役は、その機能が終わるまで Sonnet 5.5 で呼ぶ。次の機能では、また定義ファイルのモデルに戻す。
- 格上げは、権限・情報が足りない、受け入れ条件があいまい、などモデルを上げても直らない理由のときは行わない。そのときは止まってメンバーに相談する。
- 格上げしても、「止まる条件」（1機能で直してはレビューする回数が3回を超えた、など）の数え方は変えない。
- 格上げしたことは、メンバーへの報告に書く（どの役を、なぜ上げたか）。
- 役の中から別の役を呼ぶときは、格上げしない。格上げは司会役だけが行う。
  役の中から呼んだ役が `止まった` を返したら、呼んだ役はそれを自分の報告にそのまま書いて司会役に返す（格上げするかは司会役が決める）。

### 作業を始めるとき

1. `git branch --show-current` でブランチを確認する。`main`・`develop` などの上なら、メンバーに確認して
   最新の `develop` から作業ブランチを作る（`git switch -c feature/〇〇 develop` の前に `git fetch` で最新にする）。
   作業ブランチの上でも、下の「コミットするブランチの確かめ方」で、これからの作業に合ったブランチかを確かめる（`github-manager` に頼んでもよい）。
2. `.ai-tmp/<ブランチ名>/task.md` があれば読む。`handoff.md` があれば引き継ぎとして読む。
   `.agent-memory/index.md` を見て、作業に関係するチームの記録があれば読む。
3. 作業メモがなければ、メンバーと話して AGENTS.md の「8. 一時ファイルの書き方」に沿って作り、内容を見せて「はい」をもらう。
   大きさ（小・中・大）の案も司会役が出し、そう決めた理由と一緒に作業メモに書く（AGENTS.md の「大きさごとの進め方」）。メンバーが決める。
   下調べが必要なら `explorer`、機能の分け方や受け入れ条件に迷うときは `architect` を呼び、その結果をもとにメンバーと決める。

### 1機能ごとの繰り返し

1. **実装役に渡す**：`implementer` に受け渡しメモを渡す。中心になるのは次の2つ。
   - 作業メモのパスと機能の番号
   - 直すチケットのパス（2回目以降。重さ「高」「中」で、状態が `未対応` か `再発` のもの）
2. **範囲の確認**：実装役が終わったら `git status --short` と `git diff --name-only` を自分で実行し、
   変更してよい範囲の外のファイルがあれば重さ「高」のチケットにする。
3. **テスト役とレビュー役に渡す**（大きさが「中」「大」のとき。並行してよい）。大きさが「小」のときは、テスト役を呼ばず、レビュー役だけに渡す（レビュー役が「確認方法」のテストを1回実行する）：
   - `tester` へ：作業メモのパスと機能の番号。テストの結果は、レビュー役の判定を待たずに、テスト役の報告で司会役が確かめる。テストが失敗したら、その内容を重さ「高」のチケットにする。
   - `reviewer` へ：作業メモのパスと機能の番号、状態が `修正済み` のチケットのパス（直ったか確かめてもらう）。
4. **チケットを書く**：呼んだ役（テスト役・レビュー役）が返した内容から `.ai-tmp/<ブランチ名>/T-番号.md` を作る・状態を更新する
   （`修正済み` → `確認済み` または `再発`）。番号は機能ごとに 1 から。チケットは受け渡し用の一時ファイルで、記録には残さない。
5. **次へ進むか決める**：重さ「高」「中」で `未対応`・`再発` のチケットが残っていれば 1 に戻る。
   AGENTS.md の「止まる条件」に当たったら、止まってメンバーに相談する。
6. **機能を締める**：残りがなければ、重さ「低」の指摘を報告用に控えてから、その機能のチケットをすべて削除する。
   そのあと下の「コミットするブランチの確かめ方」でブランチを確かめ、その機能の変更だけをコミットする（`.ai-tmp/` は Git の対象外）。一時ファイルの中身はコミットメッセージにも書かない。
7. **テストの命令（Claude Code）**：確認方法が無いときは、リポジトリの一番上から `sh .claude/hooks/run-bridal-app-test.sh`。通ったときだけ、今の変更の指紋を `.claude/.last-test-pass` に残す。終わるときのフック（`.claude/hooks/test-bridal-app.sh`）は、この印と同じ変更ならもう一度は実行しない。実装役・テスト役・レビュー役は印を見ず、役ごとに決めた回数だけ実行する。

### コミットするブランチの確かめ方

作業の前とコミットの前に、「`main` ではないか」だけでなく、「この変更をコミットするのにふさわしいブランチか」を確かめる。
ふさわしくないブランチにコミットすると、関係のない変更が PR に混ざり、レビューと取り込みがしにくくなるため。

1. **いまのブランチの目的を知る**：`git branch --show-current` でブランチ名を、
   `git log --oneline origin/develop..HEAD` でこのブランチに積んできたコミットを見る。
2. **変更の中身と見比べる**：`git status --short` で変更したファイルを見て、ブランチの目的と合っているかを確かめる。
   - 合わない例：AI深掘りチャットの `feature/` ブランチに、ハーネス（`AGENTS.md`・`.claude/`・`.githooks/`）の変更をコミットする。
     `docs/` ブランチに `bridal-app/src` の変更をコミットする。別の機能の変更を同じブランチに混ぜる。
   - 種類の目安：新しい機能は `feature/`、不具合の修正は `fix/`、資料だけの変更は `docs/`（AGENTS.md の「5. Git のルール」）。
3. **合わなければ、ふさわしいブランチを探す**：`git fetch` で最新にしてから、次の順で候補を探す。
   1. `git branch -a` でブランチの一覧を出し、名前から目的が合いそうなものを選ぶ。
   2. 選んだブランチで `git log --oneline origin/develop..<ブランチ名>` を見て、本当に同じ目的のコミットが積まれているか確かめる。
   3. `git branch -a --merged origin/develop` で、すでに `develop` に取り込み済みかを確かめる。
      取り込み済みのブランチは使わない（新しい PR に前の変更が混ざったり、終わった PR の続きと間違えたりするため）。
      ただし、作ったばかりでまだコミットのないブランチも、この一覧に出る。2. でコミットが 0 件のものは、取り込み済みとは数えない。
   4. 目的が合い、まだ取り込まれていないブランチがあれば、それを候補にする。
      なければ、最新の `origin/develop` から新しい作業ブランチ（AGENTS.md の名前の付け方に従う）を作ることを候補にする。
4. **メンバーに確認してから切り替える**：候補のブランチ名と、それを選んだ理由（どのコミットを見て目的が合うと判断したか）を見せ、
   「はい」をもらってから `git switch` する。自分の判断だけで切り替えない。
   - 新しく作るときは `git switch -c feature/〇〇 origin/develop` のあと `git branch --unset-upstream` を実行し、
     送信先が `develop` にならないようにする。
   - まだコミットしていない変更があって切り替えられないときは、無理に進めず、止まってメンバーに相談する。

### メンバーへの報告

各機能が終わるたびに、短く報告する：変更したファイル、受け入れ条件の判定、繰り返した回数、
格上げした役とその理由、直さずに終えた指摘（重さ「低」）、確認できていない点。報告は会話の中だけで行い、ファイルには残さない。

### 送信・PR

メンバーに頼まれたときだけ、内容を見せて「はい」をもらってから、作業ブランチを送信し、`develop` 向けの PR を作る。
PR の本文には、作業メモの目的・機能ごとの結果・確認できていない点を書く。取り込みは人が行う。
PR の本文の下書きや、PR・チェックの状態の確認は `github-manager` に頼んでよい。送信と PR の作成は司会役が行う。
PR を作ったら、`.ai-tmp/<ブランチ名>/` をまるごと削除する。

### 引き継ぎとチームの記録

- 「今日はここまで」と言われたら、AGENTS.md の「7. 引き継ぎ」の順で終える。`handoff.md` の下書きは `context-manager` に頼んでよい。
  「次にやること」は、必ずメンバー本人に確かめてから書く。
- メンバーが「チームの記憶に残して」と頼んだとき、またはチームで決まったこと（技術の決定・担当範囲など）を見つけて
  メンバーが残すと決めたときは、`memory-manager` に残す内容と根拠を渡す。自分だけに関わる学びは、Claude の個人メモリに残す。

### 最新の develop を取り込むとき

PR が `develop` と衝突したとき、または `develop` の新しい変更が必要なときだけ、AGENTS.md の「5. Git のルール」の条件で行う。

1. `git branch --show-current` で自分の作業ブランチの上にいること、`git status --short` で未コミットの変更がないことを確かめる。
2. `git fetch` のあと、`git merge-tree --write-tree --name-only origin/develop HEAD` で、衝突するファイルを先に調べる。
3. 取り込む理由と衝突しそうなファイルをメンバーに見せ、「はい」をもらってから `git merge origin/develop` を実行する。
4. 衝突したら、ファイルごとに「このブランチの内容」と「develop の内容」を見せ、どう残すかをメンバーに決めてもらう。
   決まった内容で書き直し、`git add` と `git commit` で取り込みを終える。途中でやめるときは `git merge --abort`。
5. `bridal-app` に変更があればテストを実行し、結果を報告する。送信はいつもどおり「はい」をもらってから行う。
